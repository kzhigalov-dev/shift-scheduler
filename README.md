# Планировщик смен

Приложение для записи работников на мероприятия и управления сменами. Next.js 16 App Router, React, TypeScript и PostgreSQL с разграничением доступа через RLS. Интерфейс на русском, часовой пояс Europe/Moscow.

## Возможности

- Календарь и планирование месяца, создание и редактирование мероприятий.
- Виды мероприятий, шаблоны состава и ставки по должностям.
- Кабинеты менеджера и работника, заявки, отмены и распределение людей.
- Расчёт оплаты с отдельными ставками мероприятия и работника, выгрузка Excel.
- Импорт работников, смен и расписания из Excel или собственных Google-таблиц.
- Обновление названий, программ и исполнителей существующих концертов.
- Необязательный Telegram-бот: вход, уведомления, напоминания и действия из чата.
- Подписка на календарь, адаптивные экраны и светлая/тёмная тема.

## Состав публичной версии

Ветка содержит код, миграции, интерфейс и тесты. Рабочая база, реальные таблицы, контакты, токены, адрес рабочего сайта, привязки облачных проектов и внутренние документы не включены. Данные тестов и демонстрационных файлов вымышлены. Оформление и иллюстрации сохранены.

История этой ветки начинается с отдельного корневого коммита. Она не наследует прежние коммиты проекта. Публиковать следует только эту ветку; `git push --all`, `--mirror`, публикация старых тегов или слияние рабочей истории могут раскрыть прежние данные. Для публикации используйте отдельный репозиторий и отдельный remote. Изменения этой ветки не предназначены для выкладки поверх рабочего приложения.

## Локальный запуск

Нужны Node.js 24+, Docker и Supabase CLI (доступен через `npx supabase`).

```sh
npm ci
npx supabase start
npx supabase db reset
cp .env.example .env.local
npm run demo:fixtures
npm run dev
```

`db reset` сбрасывает локальную базу проекта; не запускайте его для существующей базы с нужными данными. Миграции создают структуру, виды мероприятий и должности. `seed.sql` задаёт только демонстрационный пароль локальной роли `app_user`; в облаке этот пароль использовать нельзя.

В `.env.local` заполните `MANAGER_PASSWORD_HASH`. Для получения хеша введите собственный пароль длиной от 12 символов:

```sh
read -s P && printf %s "$P" | node scripts/hash-password.mjs
```

Откройте http://localhost:3000 и войдите менеджером. Создайте работника, получите личную ссылку и откройте её в другом браузере: один браузер использует одну роль. Для импорта подготовлены вымышленные файлы `tests/fixtures/demo-staff.xlsx`, `schedule.xlsx`, `concerts.xlsx` и `google-staff.xlsx`; они генерируются из открытого кода и не входят в Git.

## Подключение собственных источников

Excel-импорт работает без Google. Для Google задайте в `.env.local` только идентификаторы собственных таблиц:

```dotenv
NEXT_PUBLIC_GOOGLE_STAFF_SHEET_ID=
NEXT_PUBLIC_GOOGLE_SCHEDULE_SHEET_ID=
NEXT_PUBLIC_GOOGLE_CONCERTS_SHEET_ID=
```

Идентификатор — часть адреса между `/d/` и `/edit`. Таблицы должны быть доступны серверу на просмотр без входа в Google. Не открывайте общий доступ к конфиденциальным данным ради импорта: в таком случае используйте Excel. Эти идентификаторы видны в браузере и закрепляются при сборке; после их изменения пересоберите приложение. Браузер выбирает только один из трёх настроенных источников, произвольные URL сервер не загружает. Если источник не настроен, приложение предлагает импорт из файла.

Для бота задайте собственные `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_USERNAME`. Ключ хранится только на сервере. Без ключа бот не отправляет сообщения. Для облачной установки настройте HTTPS-адрес, вебхук и периодический вызов `/api/telegram/tick` с проверкой секрета; сначала изучите реализацию `src/lib/telegram/` и соответствующих маршрутов.

## Проверки

```sh
npm test
npm run lint
npm run typecheck
npm run build
```

Тесты работают только с локальной базой с именем `*_test` и пересоздают её схему. Пример подключения есть в `.env.example`. Сгенерированные таблицы создаются перед `npm test`.

Проверка вёрстки — `npm run check:layout` при запущенном production-сервере на порту 3100. Для полного прогона нужна отдельная локальная база `*_layout` со всеми миграциями и импортированными демонстрационными событиями июля; основную базу для этого не используйте. Скрипт создаёт и удаляет служебные тестовые данные. Скриншоты остаются локально в игнорируемой папке `.superpowers/`. Экраны Google проверяются только для настроенных источников; без них проверяется состояние импорта из файла. При проверках Google сетевой ответ заменяется сгенерированным демонстрационным файлом.

## Публикация и секреты

Храните настройки только в `.env.local` или переменных окружения хостинга. Не добавляйте таблицы, дампы, скриншоты с личными данными и журналы работы. Перед каждым выпуском проверьте именно публикуемые файлы и достижимую историю с помощью сканера секретов, например Gitleaks. `.gitignore` помогает избежать случайного добавления файлов, но сам по себе не очищает историю.

Для облачного запуска создайте свои проекты и базу, примените миграции владельцем схемы и используйте `DATABASE_URL` с ролью `app_user`, а не владельцем таблиц. На Supabase используйте пулер в режиме транзакций. Схема сохраняет защиту RLS и проверку прав в страницах и маршрутах. Демонстрационные пароли должны быть заменены.
